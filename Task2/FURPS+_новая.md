| U3  | Загрузка справочных данных не должна превышать текущие проблемы с платежами (более секунды).|Требуется оптимизация производительности.|

| U5  | Клиент должен получать понятные уведомления о статусе заявки на всех этапах.|Повышение прозрачности процессов.|
|**R**|**Надёжность (Reliability)**        |              |
| R1  | Доступность интернет-банка и сайта должна составлять 99.9% (24/7).|Текущая архитектура с одним ЦОД не обеспечивает этот уровень.|
| R2  | Система должна автоматически переключаться на резервный ЦОД при сбое основного.|Требуется отказоустойчивая инфраструктура.|
| R3  | Заявки не должны теряться при сбоях в любом компоненте системы.|Требуется гарантированная доставка сообщений.|
| R4  | АБС должна оставаться доступной, несмотря на рост нагрузки от онлайн-заявок.|Критическое требование. Текущая БД Oracle перегружена.|
| R5  | Система кредитного скоринга должна выдерживать пиковые нагрузки в рабочие часы без деградации.|Архитектурно-значимое требование, влияющее на дизайн.|
|**P**|**Производительность (Performance)**|              |
| P1  | Время обработки заявки на кредит с паспортными данными (скоринг) не должно превышать нескольких секунд.|Требуется онлайн-интеграция с БКИ и оптимизация запросов.|
| P2  | Предодобренные кредитные предложения должны обрабатываться сотрудниками в течение рабочего дня.|Текущий batch-процесс (раз в сутки) не удовлетворяет требованию.|
| P3  | Система должна поддерживать горизонтальное масштабирование для интернет-банка и новых сервисов.|АБС масштабируется только вертикально - архитектурный конфликт.|
| P4  | Нагрузка на АБС от новых онлайн-процессов должна быть минимизирована.|Критическое ограничение из-за перегруженности БД Oracle.|
| P5  | Должна быть возможность равномерного распределения запросов между серверами и ЦОД.|Требуется балансировка нагрузки.|
|**S**|**Поддерживаемость (Supportability)**|              |
| S1  | Новые компоненты должны использовать технологии, совместимые с существующим стеком банка.|Требование снижения сложности поддержки.|
| S2  | При выборе новых технологий предпочтение отдавать тем, по которым есть экспертиза внутри банка.|Java, Python, React - существующие компетенции.|
| S3  | Для асинхронного взаимодействия использовать Kafka (как перспективное решение).|Интернет-банк на ASP.NET несовместим с Kafka - требует переходного решения.|
| S4  | Предусмотреть разработку документации для дальнейшего расширения системы.|Важно для масштабирования в будущем.|
| S5  | Новый функционал СМС должен реализовываться силами команды банка, без доработок ядра подрядчиком.|Ограничение по срокам и бюджету.|
|**+R**|**+ Ограничения (Restrictions)**   |              |
| +R1 | Новые клиенты должны проходить личную идентификацию в отделении.|Юридическое требование для банков.|
| +R2 | Чувствительные данные клиентов должны передаваться только с шифрованием трафика.|Требование безопасности (ФЗ-152).|
| +R3 | Сотрудники депозитного и кредитного подразделений не должны иметь прямого доступа к данным друг друга.|Бизнес-ограничение по безопасности.|
| +R4 | При доработках максимально использовать существующие БД (MS SQL, Oracle).|Технологическое ограничение.|
| +R5 | В текущей версии платформы интернет-банка использовать Kafka невозможно.|Техническое ограничение, требует обходного решения или модернизации.|
| +R6 | Сотрудники отделения должны работать через АБС, сохраняя существующие процессы.|Бизнес-ограничение для плавного перехода.|
| +R7 | Система кредитного скоринга не должна нагружаться дополнительными предрасчетами.|Производительность текущей системы.|
|**AR**|**Дополнительные требования (Additional requirements)**|              |
| AR1 | Внедрить систему управления ставками по депозитам (Rate Management System).|Текущий Excel-процесс не масштабируется для онлайн-каналов, создает риски ошибок и не позволяет персонализировать ставки.|
| AR2 | Создать единый реестр заявок (Unified Application Registry).|Для сквозной обработки заявок между каналами (сайт → кол-центр → отделение → бэк-офис) необходим единый источник истины.|
| AR3 | Внедрить API Gateway для интернет-банка и сайта.|Снижение нагрузки на АБС, кэширование справочных данных, маршрутизация запросов, единая точка обеспечения безопасности.|
| AR4 | Разработать план поэтапного выноса функционала из монолита АБС в отдельные микросервисы.|Перегруженность БД Oracle и невозможность горизонтального масштабирования - главные риски для роста.|
| AR5 | Внедрить систему мониторинга и алертинга для новых сервисов.|Обеспечение требований доступности 99.9% невозможно без проактивного мониторинга.|

### Ключевые архитектурно-значимые требования
1. `R4, P4` - Перегруженность АБС требует минимизации прямых обращений к ней из онлайн-каналов.
2. `P3, +R5` - Конфликт между желанием использовать Kafka и несовместимостью с текущей платформой интернет-банка.
3. `R1, R2` - Требование 99.9% доступности несовместимо с текущей архитектурой с одним ЦОД.
4. `F10` - Необходимость замены Excel-процесса управления ставками на автоматизированное решение
5. `+R3` - Ограничение на доступ между депозитным и кредитным подразделениями влияет на дизайн системы управления ставками
